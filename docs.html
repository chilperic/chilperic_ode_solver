Foko Lab operating standard

Foko Lab now has two stable surfaces: the current online legacy labs and the new model-centered workbench. This page defines when to use each surface, how Model Atlas routes into the workbench, and what the browser analyses mean scientifically.

Product surfaces

Model Atlas

Discovery layer. Each supported model should offer Open in Workbench and Open in lab. The Atlas is the recommended starting point for users.

Workbench

Model-centered analysis surface. Parameters, analyses, equations, exports and report actions are organized around one selected model.

Legacy labs

The current online labs remain available for full specialized workflows: ODE, Optimization, Steady-State, and Stochastic.

Docs and tutorial

Docs define the standard. Tutorial gives action-based routes with expected results and failure checks.

Model Atlas routing standard

Every Atlas model should make the user choose between a fast model-centered analysis path and the specialized legacy lab.

ActionUse whenRoute example
Open in WorkbenchThe user wants parameters, analysis cards, GSA/sensitivity and export from one compact page.workbench.html?model=lotka
Open in labThe user wants the full legacy lab controls, advanced plot modes, or specialized stochastic/optimization behavior.ode.html?example=lotka
Standard: Atlas cards must never route to a dead workbench model. Unsupported models must either use a reduced workbench proxy with a clear note or open only in the legacy lab.

Workbench standard

The workbench is model-centered. The first viewport should expose the model identity, parameter strip, key analysis cards and the add-analysis action. Equations and developer details belong in drawers or lower cards, not above the first analysis target.

Model header → Simulation parameter strip → Analysis cards → Add analysis → Model details drawer → Exports / report

Parameter strip

Keep the important parameters visible and editable without forcing the user into a long form.

Analysis cards

Each card owns one result type: time course, sweep, contour, GSA, diagnostics, distribution, or robustness.

Details drawer

Equations, reactions, JSON schema, generated LaTeX and low-level settings stay accessible without dominating the page.

Legacy labs

The legacy labs are not deprecated. They are the current online application and remain the complete specialist interfaces.

ODE Lab

Deterministic ODE simulation, sweeps, phase plots, advanced plots and Python export.

Stochastic Lab

CTMC/Gillespie models, ensembles, distributions, stochastic examples and exports.

Steady-State Lab

Algebraic solves, continuation, residuals and local stability interpretation.

Optimization Lab

Objective landscapes, convergence, constraints, Pareto-style views and robustness checks.

GSA and sensitivity standard

GSA must live inside the model context. A browser card may provide a quick local/range screen. Full Morris or Sobol analysis belongs in exported Python/SALib workflows.

LabelMeaningTrust level
Browser screenSmall local or range perturbation around the current model and metric.Exploratory ranking only.
Morris exportGlobal screening workflow using SALib in Python.Suitable for external validation after execution.
Sobol exportVariance decomposition workflow using SALib in Python.Computationally heavier; use outside the browser.
Trust rule: browser sensitivity must not be described as full global sensitivity unless the actual Morris/Sobol workflow is executed.

Export standard

Model JSON

Exact model state for reproducibility and later editing.

CSV

Wide CSV for spreadsheets; long CSV for tidy analysis in Python/R.

Python/SALib

External computation path for stiff ODEs, larger stochastic ensembles and global sensitivity.

Limits and trust rules

  • Browser analysis is for teaching, prototyping and fast exploration.
  • Stiff ODE validation should be exported to Python solvers such as Radau, BDF or LSODA.
  • Large stochastic ensembles should be run outside the browser after the model is checked.
  • Optimization results should be treated as approximate unless validated with a robust external solver.
  • Reduced workbench proxies are acceptable only when clearly distinguished from the full legacy model.
